# Feedback agent security boundary

The workflow accepts only parser research with explicit third-party AI consent and the relay's exact redaction schema. Ordinary user feedback cannot start a model run. The prompt and publication step both load the committed `server/src/feedback.ts` validator and its shared contracts from the untouched baseline; no second redaction allowlist is maintained.

Generation, validation, and publication use separate GitHub-hosted jobs pinned to the triggering `main` commit. Generation and validation have read-only repository permissions. There is no shared writable cache.

- Generation runs inside a disposable, unprivileged Docker container. It receives the model credential and redacted prompt, but no GitHub credential, relay credential, Docker socket, runner environment, or trusted checkout. Only the exported candidate tree and summary directory are writable mounts. After the container exits, untouched host scripts inspect and scan its proposed changes before uploading a one-day artifact.
- The handoff is bounded JSON containing full UTF-8 contents for changes to existing source and existing test files. New files, deletions, workflow/tooling/dependency changes, extra fields, duplicate paths, symlinks, and binary content cannot be published. Untracked scratch files are not included. The consumer validates the payload and current baseline paths again.
- Validation creates independent baseline, test-only, and complete-change trees. Each suite runs inside a fresh container with networking disabled, a read-only dependency image, no secrets, and only its own disposable tree writable. The baseline must pass, the test-only change must fail, and the full change must pass. The host records a digest of the exact validated JSON before executing candidate tests.
- Publication downloads that same artifact onto a fresh runner, verifies its digest and paths, re-fetches the original consented feedback, and repeats the diagnostic copy scan. It never checks out candidate code, runs package commands, applies patches, imports candidate modules, or invokes Git hooks. Trusted code sends candidate file contents to GitHub's tree/commit API as data. It refuses stale `main`, creates a new branch per run attempt, and opens a draft PR. No force update or merge occurs.

The copy scanner compares the fixed report label and actual diagnostic templates against the summary and changed file contents. It normalizes Unicode and whitespace, checks complete templates of 16–59 characters, and checks 60-character windows for longer templates. It never prints matching text. Raw feedback, model output, and candidate test logs are not uploaded or printed.

The disposable `/tmp` tmpfs explicitly permits execution while retaining `nosuid` and `nodev`. Sender-registry parity tests compile native Swift programs there and must execute them; Docker's default `noexec` mount prevented execution despite successful compilation. This affects only the already code-executing generation/validation containers, not the separate publication runner. Validation remains offline, unprivileged, and unable to write its root filesystem. Native launch failures report the process error code, and regression coverage distinguishes `EACCES` from a successful scratch-program launch.

Generation and each validation tree first run the installed Expo CLI's iOS prebuild with `CI=1 EXPO_OFFLINE=1` and `--no-install`. Expo 55 uses its bundled native template, so this creates the ignored iOS files required by the contract suites without installing dependencies or accessing the network. Setup failure stops the model or tests. Generated untracked native files are excluded from candidate collection; any unexpected tracked dependency change still fails the publication path restriction.

This is a best-effort copy check. It does not prove that text has not been paraphrased, encoded, or deliberately transformed. A red/green suite also cannot prove that agent-written assertions are honest. Human review remains required for the entire draft. The sandbox restricts runner persistence and publication privileges; the model process still needs its own credential and network access to call its provider.

The CLI is pinned to `@anthropic-ai/claude-code@2.1.269`, verified against the npm registry on 2026-09-12. GitHub actions are pinned to the full SHAs resolved from each official action's v4 tag on that date. Both Docker images use the official Swift 6.2.4 Bookworm compiler/runtime image and copy Node 22.22.3 with npm 10.9.8 from the official Node Bookworm image. Both image indexes are pinned by digest, with AMD64 and ARM64 manifests verified on 2026-09-19. Node/npm version assertions and a Swift compiler check fail the build before dependency installation if a toolchain is missing or mismatched. The Swift toolchain keeps the sender-registry compilation, execution, and TypeScript/Swift parity assertions enabled in the full suite; it does not provide Xcode or iOS SDK validation. Debian package updates remain governed by the image's package repository.

Local regression coverage is in `scripts/test/workflows/feedback-security.test.cjs`, included by the existing workflow-test glob. It exercises diagnostic leak rejection, consent and schema rejection, unsafe payload paths, and API publication with deliberately planted hooks and executable candidate text. It also checks the job/credential separation. A live model-to-draft-PR run still requires configured repository secrets and explicit operational authorization; local checks do not claim such a run occurred.

Toolchain provenance: [official Swift image definitions](https://github.com/docker-library/official-images/blob/master/library/swift), [Swift 6.2.4 Bookworm Dockerfile](https://github.com/swiftlang/swift-docker/blob/ef2c1e72ea88715a5b8c632b26bbf835a0c7bf4b/6.2/debian/12/Dockerfile), and [Node 22.22.3 release including npm 10.9.8](https://nodejs.org/en/blog/release/v22.22.3).

Both images install the JDK for Java regex checks, SQLite for schema checks, Python 3 for workflow-script AST checks, and Make for native dependency builds. The shared interaction-test runner limits file concurrency to two workers, keeping contention comparable to the CI baseline without skipping suites or relaxing timing assertions.
