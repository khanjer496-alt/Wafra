# Wafra 1.0.2: online logos, store forms and privacy policy

Wafra 1.0.2 loads every merchant and bank logo online from Brandfetch, on by
default on iPhone and Android, with no switch or consent step. 1.0 and 1.0.1
send nothing for logos. These three things must change **before 1.0.2 is
submitted**. Nothing here has been changed in Play Console, App Store Connect
or on the website.

## What leaves the phone

| | |
|---|---|
| Where | `api.brandfetch.io/v2/search/<name>?c=<client id>` (Brand Search) and `cdn.brandfetch.io/domain/<domain>?c=<client id>` (Logo API image) |
| What | A cleaned merchant name from the user's transactions, or a bank name from their accounts: at most 80 characters, with amounts, card/account tails, payment-processor prefixes, city/terminal tails and URLs stripped (`merchantBrandCandidate`, `brandfetchSearchUrl`). For a known brand, only its domain. |
| Never | Amounts, dates, account or card numbers, balances, bank message text, user or device IDs |
| Identifiers | None. The client ID is the same for every install, and on iPhone and Android every search and image request sends `Referer: https://wafra-app-azg.pages.dev/` (the origin of `extra.privacyPolicyUrl` in `app.json`), the same for every install; the web build sends the browser's own. Brand Search requests send no cookies (`credentials: 'omit'`); logo images load through expo-image, which uses the system cookie store, but Brandfetch's hosts set no cookie (checked 13 Nov 2026). Brandfetch sees the IP address and the User-Agent. |
| When | After the ledger loads, in an idle callback, for merchants and banks on screen. Search results are kept **in memory for the current app session only** (at most 128 merchant and 64 bank names; nothing is written to storage), so a list does not search the same name twice. Images are hotlinked from `cdn.brandfetch.io`; Wafra keeps no image files of its own, and expo-image's normal HTTP cache applies. Onboarding also loads the example bank logos for the selected region from the CDN (fixed example domains, no user data). |
| Off | Only with the saved local-only preference from earlier versions. There is no switch in 1.0.2. |
| Deletion | Search results disappear when the app quits; **Erase all data** clears them at once. The first launch of 1.0.2 deletes any search results that pre-1.0 builds stored on the phone. Images in expo-image's HTTP cache stay until it evicts them. |

## Google Play Data safety

Before 1.0.2 the form does not declare logo lookups (Android sent nothing).
Change these answers in Play Console, App content, Data safety:

1. **Data collection and security**
   - "Does your app collect or share any of the required user data types?" Yes (unchanged).
   - "Is all of the user data collected by your app encrypted in transit?" Yes (Brandfetch is HTTPS only).
2. **Data types**, add or confirm:
   - **Financial info > Purchase history**: tick *Collected* and *Shared*. Merchant names come from the user's purchases.
   - **Financial info > Other financial info**: tick *Collected* and *Shared*. Bank names come from the user's accounts.
3. **For each of those two types**, for the logo flow:
   - Is this data processed ephemerally? **No.** Brandfetch's own retention is not documented to us.
   - Is this data required for your app, or can users choose whether it's collected? **Required.** There is no switch in 1.0.2. If either type is already declared *Optional* for another feature (statement upload), set it to *Required*, because one answer covers every flow of that type.
   - Why is this user data collected? **App functionality.**
   - Why is this user data shared? **App functionality.**
4. **Shared, not service provider.** Brandfetch runs its own service under its own terms rather than processing only on Wafra's instructions, so declare *Shared* rather than relying on the service-provider exemption. If counsel decides Brandfetch qualifies as a service provider, untick *Shared* for both types.
5. Leave "Data deletion" as it is: nothing is stored on Wafra's servers or written to the phone's storage for this flow.

## Privacy policy

Replace the "Merchant and bank logos" paragraph in `docs/privacy-policy.md`
(and the published page) with:

> **Merchant and bank logos:** to show a merchant's or bank's logo, Wafra sends
> only a cleaned merchant or bank name, never the amount, account or card
> number, or bank message, to Brandfetch, a logo service, and then loads that
> brand's logo from Brandfetch. Brandfetch can see the name, the brand's web
> address and your network address; no account, device or user identifier is
> sent. This is on by default on iPhone and Android. A saved local-only
> preference from an earlier version turns it off. Wafra does not store the
> lookup results: they are kept only while the app is open. Logo images load
> directly from Brandfetch, and your phone's image cache may keep a copy for a
> while. If no logo is found or you are offline, Wafra shows the name's first
> letter. Widgets show letters only.

The in-app privacy sheet (Settings, Messages privacy) already shows the same
statement in English and Arabic (`privacyLogosBody` in `src/lib/i18n.ts`).

## Brandfetch account and terms (owner)

- **Client ID.** The app uses `EXPO_PUBLIC_WAFRA_BRANDFETCH_CLIENT_ID`, falling
  back to the client ID already in `src/lib/verified-logo-identities.ts`. It is
  not set in `app.config.js` or `eas.json`; check whether EAS "production"
  environment variables set it. On 28 Nov 2026 the fallback ID returned a
  redirect to an image from the CDN (an invalid ID returns 403) and 200 from
  Brand Search, so it is still valid. Confirm it belongs to Wafra's Brandfetch
  account.
- **Free plan.** Brandfetch's Logo API is free up to **1,000,000 requests a
  month** (a soft fair-use limit; far beyond it Brandfetch can answer 429),
  needs no attribution, and its client ID is "public and safe to use in frontend
  code" (Brandfetch Logo API docs). Throughput limits also apply: 1,000 requests
  per 5 minutes per IP and 2,400 per 5 minutes per customer. Session-memory
  results and the idle-time, on-screen-only lookups keep Wafra well inside these
  at today's install count; watch the Brandfetch dashboard as installs grow.
- **How 1.0.2 follows Brandfetch's terms** (decision 28 Nov 2026, instead of a
  plan change):
  - "Brand Search results must not be stored at all": search results are no
    longer written to the phone. They live in a bounded in-memory map for the
    current session only, so a list does not search the same name twice; erase
    and quitting the app clear it. Results pre-1.0 builds stored are deleted on
    the first launch of 1.0.2 (`removeStoredLogoSearchResults`).
  - "Logo API images must be hotlinked rather than stored": every image is
    requested from `cdn.brandfetch.io` by its Logo API URL and drawn from that
    response. Wafra adds no image store of its own and does not copy or bundle
    logos. expo-image's ordinary HTTP cache still applies (cache policy left as
    it was: `memory-disk` on iPhone, `disk` on Android), the same way a browser
    caches a hotlinked `<img>`. Offline use is not a goal: with no network and no
    cached response, the letter shows. If Brandfetch reads its terms as excluding
    an HTTP cache, set `cachePolicy` to `none` in the two avatars.
  - "HTTP requests must include the Referer header": native search and image
    requests send `Referer: https://wafra-app-azg.pages.dev/`; the web build
    relies on the browser's default Referrer-Policy
    (`strict-origin-when-cross-origin`, which Brandfetch accepts).
- **Optional follow-up.** If **Erase all data** should also remove downloaded
  logo images, it can call expo-image's `Image.clearDiskCache()` and
  `Image.clearMemoryCache()`; that clears every cached image in the app, so it
  is left as a product decision.
